# コードコメント

- プロジェクト側にコメント規約（CLAUDE.md / rules / lint 設定）があればそちらを優先する（MUST）
- コードから読み取れることを書かない。実況型の WHAT コメント（例: `// ユーザー ID を取得`）を書かない（NEVER）
- 変更履歴をコメントに書かない。「〜を追加した」「かつて〜だった」「旧実装では〜」「〜の方針だったが〜に変えた」は git log / PR 本文に書く（NEVER）
- タスク ID・チケット番号への参照だけのコメントを書かない。リンク先が消えると識別子だけ残る。必要な背景は本文に書く（NEVER）
- 書いてよいのはコード単独では判断できない知識のみ: 外部制約（ライブラリ・API の仕様）、直感に反する実装を選んだ理由、過去のバグの教訓（「なぜ」に限定し経緯は書かない）
- 迷ったら書かない。長いコメントで補強したくなるのは実装に自信がないサイン。先にコードで表現できないか検討する（SHOULD）
