# /commit

1. リポジトリの CLAUDE.md と `.claude/`（commands / skills）にコミット規約・品質ゲートがあれば読み、それに従う。リポジトリ固有の /commit 相当の手順が定義されている場合はそちらを優先する
2. `git log --oneline -10` でコミットメッセージの言語・形式を確認し、同じスタイルで書く
3. `git status` と `git diff` で変更をレビューし、無関係な変更が混ざっていれば分割を提案する
4. 変更ファイルをパス指定でステージする（`git add -A` / `git add .` 禁止）。secrets・巨大バイナリが含まれていれば停止して報告する
5. リポジトリに品質ゲート（lint / typecheck / test 等）があれば変更範囲に対して実行し、green を確認してからコミットする
6. **コミットメッセージは原則1行**（下記）
7. push はしない。push は別途明示的な指示があった場合のみ

## コミットメッセージ

**原則1行。** 1行で何をしたかが明確に伝わることが最も重要で、本文で補うのはその代わりにならない。

- 件名だけで意味が通るように書く。曖昧な件名を本文で説明しようとしない
- `Co-Authored-By` などの trailer は**付けない**
- 変更が1行で言い表せないほど大きいなら、まずコミットの分割を検討する
- リポジトリの既存コミットに独自の規約（言語・prefix・trailer）があればそちらを優先する

本文を書いてよいのは、**1行では伝わらず、かつ後から読む人が必要とする情報がある場合だけ**。典型的には次のもので、いずれも「何をしたか」ではなく**「なぜそうしたか」**を書く。

- 非自明な判断の理由・却下した代替案
- 挙動の破壊的変更や、移行に必要な手順
- 一見無関係な変更が同じコミットに入っている理由

本文を書く場合も簡潔にまとめる。差分を読めば分かる変更内容を列挙しない。
