# /fleet

ハブ（workspace `entry`）の Claude が、各リポジトリの pane で動く Claude に作業を委譲するための手順。
操作は `fleet` コマンドに集約してある。`herdr` を直接叩くのは `fleet` で足りないときだけにする。

## ハブと担当範囲

ハブは `entry` workspace の各タブに置いた Claude。クライアントごとにタブを分け、ユーザーはタブを切り替えて相手を選ぶ。`fleet` は `entry` workspace 以外では動かない。リポジトリ側の agent として動いているときはこの skill を使わず、自分で作業する。孫への再委譲はしない。

担当範囲はそのハブ pane の cwd から決まる。`~/<root>` を cwd にしたタブはその root 専用で、`~` を cwd にしたタブは他のタブが持たない root をすべて担当する。設定ファイルは要らない。別の場所にあるが同じクライアントの作業というルートだけ `~/.config/fleet/roots` で寄せる。

担当外のターゲットは `fleet` が拒否する（終了コード 8）。そのときは**自分で回り込まず、どのハブタブから投げるべきかをユーザーに伝える**。クライアントの業務内容をハブのコンテキストに混ぜないための境界なので、`--any-scope` で越えない。

```bash
fleet scope    # このハブの担当範囲と、他のハブタブが持つ root
```

依頼先が今いるリポジトリ自身なら委譲しない。自分でやる。

## 投げる

```bash
fleet targets                      # 担当範囲の候補・workspace・agent 状態（JSON）
fleet send <target> --prompt '...'  # workspace と agent を用意して投入（非同期）
```

`send` は `ensure` を内包するので、workspace が無ければ作り、agent が居なければ起動し、既存の idle agent があれば再利用して slug 名を付ける。アクティブなリポジトリだけ workspace を持つ運用なので、事前に全リポジトリを用意したりはしない。

- target は slug / workspace ラベル / `~` からの相対パス / 絶対パスで指定する
- `ターゲットが曖昧` （終了コード 3）で候補が返ったら、**推測せずユーザーに確認する**
- 複数リポジトリへ投げるときは `fleet send` を並べて実行する。待たない
- 完了まで待つ必要があるときだけ `--wait [--timeout MS]` を付ける
- 前の依頼と別のタスクを投げるときは `--fresh` を付ける（送る前に `/clear` する）。前の文脈が無いので、依頼本文は単独で読める形にする。同じタスクへの追加・訂正・続きは付けない。agent が待機中でないと失敗する
- 本体と切り離したいときだけ `--branch <name>` で worktree workspace を使う
- プロンプトが長い・改行を含むなら `--prompt-file` か `-`（標準入力）を使う
- `--model` でモデルを、`--kind` で agent の種類を選ぶ（下記）

依頼本文には「何を達成したいか」と受け入れ条件を書く。`fleet` が運用ルール（作業ディレクトリ、報告先、自律範囲）を自動で添えるので、それを手で書き足さない。

## モデルと agent の種類を選ぶ

`--model` を付けないと、起動時のプロファイル設定のモデルになる。**依頼の重さに見合うモデルを選ぶ。**

- 調査・読み取り・定型の修正 → 軽いモデル（`haiku` / `sonnet`）
- 設計を伴う実装、広範囲の変更、原因の分からない不具合 → 重いモデル（`opus` / `fable`）
- ユーザーがモデルを指定したらそれに従う。迷う規模なら聞く

起動済みの agent に `--model` を付けると、投入前に `/model` を送って切り替える。会話は維持される。切り替えはそのセッション全体に効くので、軽い用途で切り替えたまま重い依頼を投げないよう、依頼ごとに意識して指定する。

`--kind` の既定は `claude`。別の種類を使うときは次を踏まえる。

- agent 名が `<slug>-<kind>` になるので、同じリポジトリで claude と併存できる
- 実行ファイルが PATH に無ければ起動前に止まる
- **claude 以外は規約ファイルの読み方が違う。** CLAUDE.md を読まない agent もあるので、守らせたい規約は依頼本文に書く
- `herdr integration status` で lifecycle 検出の導入状況が分かる。未導入だと idle / blocked の判定が鈍る。導入はユーザーの判断に任せ、勝手に入れない

## クラウドで実行する

ユーザーが「クラウドで」「クラウド実行で」と言ったら、pane ではなくクラウドセッションに投げる。長時間かかる作業、手元のマシンを占有したくない作業、成果を PR で受け取りたい作業に向く。

```bash
fleet cloud <target> "<セッション名>" [--model M]
```

`claude --cloud` はセッションを作って即終了し、pane には残らない。したがって herdr の agent にはならず、`fleet send` の経路は使えない。`fleet cloud` はセッションを作って `session_id` / `url` / `session_name` / `contract` を返すだけで、**依頼本文は作成後に SendMessage でそのセッションへ直接送る。**

- 送り先は出力の `session_name`。**作成直後は ListAgents に現れないことがある**ので、見つからなければ少し待って確認する
- 依頼本文には出力の `contract` を添える。クラウドでは成果の受け渡しが PR になるため、ローカル用の契約とは別物
- クラウドセッションはこちらに返信できない。**返信を求める書き方をしない。** 結果は PR で受け取る（`gh pr list` / `gh pr view`）
- クラウド側のクローンはリモートから作られる。ローカルの未コミット変更は見えないので、必要なら先に push する。`fleet cloud` は汚れた作業ツリーを警告する
- `--teleport` は使わない。**ローカルの作業ツリーのブランチを切り替えてしまう**
- origin が無いリポジトリでは使えない

クラウド実行を選ぶことは、push と PR 作成を許可することを含む。ローカル実行の「PR は指示時のみ」とは前提が違う。

## 子 agent の自律範囲

`fleet` が添える契約で、子 agent は **実装とコミットまで自律的に進める**。push と PR 作成は、リポジトリの規約（CLAUDE.md 等）か依頼本文が許すときだけ行い、どちらにも定めが無ければしない。デプロイ・マージなど外部サービスへの変更はしない。必要なら report に「要指示」として書いて止まる。
これを変えたいときは依頼本文に明示する（例: 「調査だけして変更しない」「push まで済ませる」）。

## 回収する

```bash
fleet status            # 全 agent の状態 + report の到着状況
fleet report <target>   # 最新 report を読む
```

`fleet send` は非同期で、終わっても通知は来ない。**投げたら毎回、同じ target で `fleet watch <target>` をバックグラウンド実行する**（Bash の `run_in_background`）。report が届くと report を出力して終了し、その終了通知で回収のタイミングが分かる。承認待ちになったときも終了する（終了コード 5）。worktree の target はラベル（`<repo>#<branch>`）で指定する。続きの依頼を同じ target に投げ直したら、前の watch は古い report を見ていないので、そのまま新しい report まで待つ。

子の回答は pane からは読み取れない（Claude Code は代替スクリーンで動くため）。回収は必ず report ファイル経由で行う。`fleet status` の `reports_unread` に出たものを `fleet report` で読む。

`blocked` は承認待ちか質問待ち。**勝手に答えない。** `herdr agent read <agent名>` で何を聞かれているか確認し、ユーザーに判断を仰ぐ。

report に「要確認」「要指示」があればユーザーに取り次ぐ。続きを頼むときは同じ target に `fleet send` を投げ直す（会話は継続する）。

## ユーザーへの報告

report を貼り付け直さない。リポジトリごとに「何が終わったか / 判断を待っているもの / 残課題」を数行でまとめ、詳細が必要なときに report のパスを示す。

## プロファイル

親ディレクトリによって direnv が Claude プロファイル（`CLAUDE_CONFIG_DIR`）と GitHub アカウント（`GH_CONFIG_DIR`）を切り替える。`fleet ensure` / `fleet send` の出力の `profile` が `default` 以外なら、そのリポジトリは別プロファイル・別アカウントで動いている。ハブ側から `gh auth switch` をしない（グローバルに効いて他のリポジトリを壊す）。

`.envrc` を変更した場合、既に起動している agent の環境は古いままになる。`profile` が期待と違うと報告されたら、その pane で Claude を終了して `claude --continue` で再開するようユーザーに伝える。

## 片付け

作業が終わって不要になった workspace は `fleet close <target>` で閉じる。`fleet` が作ったものだけが対象で、それ以外は `--force` が必要。**ユーザーの明示指示がない限り閉じない。**
